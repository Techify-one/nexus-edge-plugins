# Paridade funcional do Financeiro

Comparação com `Techify-one/nexus-financeiro` em `07fdd19f8084e636ef220b7a104aa2f5e52509f2`, baseada na leitura de controllers, serviços e testes originais, especialmente `test/live/dinheiro.live.spec.ts` e `test/live/recorrencias-fechamento.live.spec.ts`.

Estados: implementado significa código presente; validado localmente significa cenário executado no motor indicado. Nenhum desses estados significa instalação confirmada no hub ou equivalência integral com o original.

## Diferenças de contrato intencionais

- O plugin roda no contrato do Nexus Edge, não em Nest/Next/Prisma.
- Rotas usam query `empresaId`; os IDs são próprios do plugin, não UUIDs/keys antigos garantidos.
- Competência é data civil no DTO atual, não somente `YYYY-MM` como no original.
- Datas de movimento usam `dataEfetiva`; idempotência usa `chaveIdempotencia` no corpo.
- Situação liquidada é `LIQUIDADO`, não o `QUITADO` antigo. Códigos HTTP/erros também não são uma API compatível byte a byte.
- Dados históricos, empresas, credenciais, anexos e saldos do Nexus antigo não são importados.
- Fluxos exclusivos de plataformas e MCP próprio não são reintroduzidos.

## Limites da evidência

Os testes de serviço exercitam implementação e migrations reais, mas não fazem uma implantação completa do Worker atrás do gateway. Testes HTTP usam `app.request` com binding D1 local e contexto interno sintetizado apenas no ambiente isolado. O PostgreSQL de teste não é banco do usuário. Scripts browser.integration.mjs e frontend.browser.mjs registram a execução real do Chromium, com a autoridade dos dados de cada fixture explícita. Nenhum acesso financeiro de produção foi necessário.
